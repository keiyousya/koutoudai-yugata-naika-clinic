# agent-mail への issue 起票

依頼内容: $ARGUMENTS

## 前提

- 起票先は **`keiyousya/agent-mail`**（private）。このリポジトリ（clinic）の issue ではない。
  - clinic 側の #24〜#27 は過去に clinic に立てたもの。今後の事務タスクは agent-mail に立てる。
- `gh` は tamurakeito アカウントで認証済み。`gh issue create -R keiyousya/agent-mail` で立てる。
- ラベルは使っていない。

## 書き方

タイトルは `[事務] <相手や対象>への<やること>` にする。
例: `[事務] アルファシステムへORCAのOASCIS用UKE出力を問い合わせ`

本文は次の構成にする（不要な節は省く）。

```markdown
## 概要

何を、誰に、何のためにするかを1〜2文で書く。

## 背景

- 事実を日付つきで箇条書きにする（例: 2026-09-21 時点で〜）
- 経緯の詳細は clinic リポジトリのパスで示す（例: clinic リポジトリの `filings/kouseikyoku/<案件>/`）
- 締切があれば書く

## 下書き

さくらメール 下書き（INBOX.Drafts uid NNNN）
宛先: <アドレス>
件名: <件名>

## 次のアクション

- [ ] 下書きを確認して送信する
- [ ] 回答を受けて〜する
```

- **1つの相手・1つの用件につき1 issue**。問い合わせ先が2つあれば2件に分ける。
- メールの下書きがあるときは、フォルダと UID・宛先・件名を「下書き」節に残す（本文は貼らない）。
- 次のアクションは、送信 → 回答待ち → 回答を受けてやること → 締切のある作業、の順にチェックボックスで並べる。

## 書かないもの

- 患者の個人情報、ログインID・パスワード・トークン類
- メール本文の全文（下書きの場所を書けば足りる）

## 起票後

1. 作成された issue の URL をユーザーに返す。
2. 案件の README（`filings/` や `shisetsu-kijun/` など）に経緯を書いている場合は、
   「agent-mail issue N」と参照を追記する。本文中に `#N` と書くと GitHub が自リポジトリの issue へ自動リンクしてしまうので避ける。
